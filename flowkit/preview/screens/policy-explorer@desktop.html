01 / FOLLOW THE STATE

From request to outcome.

Select a state to jump to its rule.

01NEWStart here02IDENTIFIEDCheck identity03TRIAGEDCheck the request04PAYINGExecute once per visit05DONEOutcome: act
↳ESCALATEDOutcome: escalate

Unknown customer, unknown payee, over limit, agent handoff, failure, or stall.

This shows the main payment path. The escalate signal can move any non-ESCALATED state to ESCALATED, including DONE; final states are outcomes, not immutable locks.

02 / OPEN THE RULEBOOK

Eight rules. No hidden permission.

Expand a rule to see its exact condition.

Order matters.

Automatic rules are checked in file order; the first true condition fires. Signal rules respond to a matching agent tool call. Unknown facts do not make a condition true.

03 / WHAT THE POLICY KNOWS

Seven facts, with defined types.

The agent cannot write these fields directly.

customertext

The customer identified from the sender’s records.

limitmoney

The customer’s recorded spending limit.

amountmoney

The exact amount in the request data.

payeetext

A requested payee already saved for this customer.

categoryenum

payment · question · complaint · other

paidbool

Whether the payment function recorded success.

reasonenum

UNKNOWN_CUSTOMER · UNKNOWN_PAYEE · OVER_LIMIT · ACTION_FAILED · AGENT_ESCALATED · NOT_HANDLED

Functions, classifier answers, and rule assignments establish facts. Missing information stays unknown until established; money uses exact decimal values.

05 / WHEN THE PATH BREAKS

Failure has a destination, too.

On error

ACTION_FAILED

The policy-wide error handler records a failed action and moves to ESCALATED. The payment rule defines the same local fallback.

On stall

NOT_HANDLED

If the agent stops before closing the case, the stall handler moves it to ESCALATED, with the reason recorded.

Retries & execution boundaries+

Triage allows 1 retry; make_payment allows 2 retries. The pay signal only changes state. The payment function is called by an automatic rule, once per visit to PAYING. External functions still need idempotency protection; the policy alone does not guarantee exactly-once side effects across retries or restarts.

Snapshot of track/policy.yaml used for this report. This explorer explains the policy; it does not edit it or execute payments.

# The track: a starting point for a payments desk. Replace and extend it for the event's track.
#
# How to read it: a case starts in NEW. Rules with no `on:` run by themselves, top to bottom,
# the first true one each time. Rules with `on:` answer the agent's signals (its tools). The
# agent never writes a field: functions and the classifier do. A case ends in a `final:` state,
# and that state is the answer.
#
# Convention: a rule with `on:` only moves the case (`set:`, `to:`); code runs in rules with no
# `on:`, fired by the state. A signal never calls a function directly, and a rule with no `on:`
# fires once per visit to a state, so the agent cannot make a payment twice.

policy: payments-desk
version: 1
description: >
  A bank's operations inbox. Customers ask for payments to be made; the desk pays a payee the
  customer already has, within the customer's limit, and hands everything else to a person with
  the facts attached.

fields:
  customer: { type: text,  description: the customer the sender is }
  limit:    { type: money, description: what the desk may pay for this customer without asking }
  amount:   { type: money, description: "the amount asked for, from the request's data" }
  payee:    { type: text,  description: "a payee the customer already has, from the request's data" }
  category: enum [payment, question, complaint, other]
  paid:     bool
  reason:   enum [UNKNOWN_CUSTOMER, UNKNOWN_PAYEE, OVER_LIMIT, ACTION_FAILED, AGENT_ESCALATED, NOT_HANDLED]

states: [NEW, IDENTIFIED, TRIAGED, PAYING, DONE, ESCALATED]
initial: NEW
final:
  DONE: act
  ESCALATED: escalate

signals:
  pay:
    description: >
      Make the payment the customer asked for. The desk pays the amount and the payee from the
      request's data, never from your words, and only to a payee the customer already has within
      their limit. Use it once, for a payment request only.
  escalate:
    description: >
      Hand the case to a person now. Use it when the case is outside what the other tools do,
      when facts conflict, or when you are not sure. Say what a person needs to know.
    args:
      note: { type: text, description: "what happened and what is still open, for the person" }

triggers:
  # --- who wrote? Facts come from the records, not from the message.
  - name: identify
    when: "state = NEW"
    call: find_customer
    to: IDENTIFIED

  - name: unknown-customer
    when: "state = IDENTIFIED and customer absent"
    set: { reason: UNKNOWN_CUSTOMER }
    to: ESCALATED

  # --- what is it about?
  - name: triage
    when: "state = IDENTIFIED and customer present"
    ask:
      category:
        choice: "What is the message mainly about?"
        options:
          payment: a request to pay someone or move money
          question: a question about an account or a payment
          complaint: a complaint or a dispute
          other: anything else
    retry: 1
    to: TRIAGED

  - name: unknown-payee
    when: "state = TRIAGED and category = payment and payee absent"
    note: The payee is not one the customer already has, so a person checks it.
    set: { reason: UNKNOWN_PAYEE }
    to: ESCALATED

  - name: over-limit
    when: "state = TRIAGED and category = payment and amount > limit"
    note: Over the customer's limit, so a person decides.
    set: { reason: OVER_LIMIT }
    to: ESCALATED

  # --- the agent asks to pay: the signal only moves the case on.
  - name: pay-requested
    on: pay
    when: "state = TRIAGED and category = payment and payee present and amount <= limit"
    to: PAYING

  # --- the payment itself: fired by the state, once.
  - name: pay
    when: "state = PAYING"
    call: make_payment
    retry: 2
    on_error: { set: { reason: ACTION_FAILED }, to: ESCALATED }
    to: DONE

  # --- the agent hands over.
  - name: agent-escalates
    on: escalate
    when: "state != ESCALATED"
    set: { reason: AGENT_ESCALATED }
    to: ESCALATED

on_error:
  set: { reason: ACTION_FAILED }
  to: ESCALATED

on_stall:
  set: { reason: NOT_HANDLED }
  to: ESCALATED

briefing: brief

agent:
  model: claude-sonnet-5-5
  max_turns: 6
