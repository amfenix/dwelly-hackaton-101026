04 / WHAT THE AGENT CAN ASK

8 tools. Bounded authority.

ask_system

The answer the customer needs is not in the case yet: ask the system that holds it.

system payment: transfers, payments, batches; incoming: money into the account; recurring: standing orders, Direct Debits; card: cards, card payments; access: sign-in, devices; business: company limits, roles, signing, imports; documents: statements, exports, reports; tariff: fees and charges

reply

A system's answer is in the case: reply to the customer within it. The desk writes the reply.

submit_request

Pass a dispute, a review or a return to the team that handles it, or a verified customer's clear instruction (block a card, cancel a mandate) to the system that carries it out.

clarify

The case does not say which payment, card or instruction is meant: ask the customer. The desk writes the question.

need what is missing

redirect_secure

Signing in, recovery, a PIN or a password: point the customer to the bank's secure process.

forward_to_authority

The request needs someone else's approval (a company administrator, a second signatory): send it to that person.

refuse

A last resort, when the bank can do what was asked in no permitted way: someone else's account, another person's login or a code, PIN or password, a request from someone without the authority, a change to a joint account by one holder. Name the reason; the desk writes the reply with the permitted route. Not when the request can be forwarded or checked instead.

reason why the bank cannot do it

escalate

Nothing above fits, or the facts conflict: hand the case to a person.

note what a person needs to know

05 / WHEN THE PATH BREAKS

Failure has a destination, too.

On error

ACTION_FAILED

Moves to ESCALATED.

On stall

NOT_HANDLED

If the agent stops before closing the case, it moves to ESCALATED.

# Design: docs/policy-design.md. Facts come from track/functions.py, which reads the case's
# history (docs/task/target-api.md); the agent reads the conversation and the facts and sends the
# decision as a signal; a rule accepts it only when the facts support it.
#
# Convention: a rule with `on:` only moves the case (`set:`, `to:`); the work is done by a rule
# with no `on:`, fired by the state, once. Every final state is a decision.

policy: banking-desk
version: 1
description: >
  A bank's service desk (Harrow & Vale Bank, fictional). The bank never acts or approves for
  someone else, never handles a PIN or a password, and never claims more than a record shows.

fields:
  # --- who is asking (identify_requester)
  requester: { type: text, description: the customer's name as written }
  role:      enum [customer, business_admin, signatory, uploader, viewer, employee, third_party]
  channel:   enum [secure_portal, secure_chat, verified_call, business_portal, external_message]
  verified:  { type: bool, description: the request came through a verified channel or after identity checks }
  # --- what it is about (find_subject)
  subject:      enum [transfer, incoming_payment, standing_order, direct_debit, card, card_payment, batch, payment_package, profile, access, statement, document, fee, limit, role]
  amount:       money
  counterparty: text
  reference:    text
  subject_date: date
  # --- what the systems answered (check_*)
  payment_asked:      bool
  payment_status:     enum [SENT, PENDING, AWAITING_AUTHORISATION, COMPLETED, DECLINED, NOT_EXECUTED, REJECTED, CANCELLED, OTHER]
  payment_reason:     text
  payment_count:      number
  incoming_asked:     bool
  incoming_found:     bool
  incoming_amount:    money
  recurring_asked:    bool
  recurring_status:   enum [ACTIVE, CANCELLED, NOT_EXECUTED, AMENDED, OTHER]
  next_run:           date
  card_asked:         bool
  card_status:        enum [REQUESTED, IN_MANUFACTURE, DISPATCHED, BLOCKED, RESTRICTED, DECLINED, OTHER]
  card_reason:        text
  access_asked:       bool
  access_status:      enum [RESTORED, AWAITING_CONFIRMATION, LINKED, PROCEDURE_STARTED, EXTRACT_PROVIDED, OTHER]
  business_asked:     bool
  business_status:    enum [RECEIVED, VALIDATION_FAILED, AWAITING_SECOND_SIGNATORY, PENDING_APPROVAL, ROLE_REVOKED, OTHER]
  business_limit:     money
  documents_asked:    bool
  document_ready:     bool
  document_name:      text
  tariff_asked:       bool
  tariff_status:      enum [MATCHES, MISMATCH, OTHER]
  # --- what the bank already did in the conversation (check_bank_actions)
  bank_redirected:    bool
  bank_forwarded:     bool
  bank_clarified:     bool
  registration_asked: bool
  registered:         bool
  registration_ref:   text
  # --- has the customer confirmed a change (check_confirmation)
  confirmation:              enum [none, requested, given, unprompted]
  instructed_outside_portal: bool
  # --- the policy's own
  request_type: enum [question, register, change, instruction, access, authority, other]
  next_system:  { type: enum, values: [payment, incoming, recurring, card, access, business, documents, tariff], description: the system that holds the answer }
  reason:       enum [UNVERIFIED, OUTSIDE_PARTY, AGENT_ESCALATED, ACTION_FAILED, NOT_HANDLED]
  clarify_need: { type: enum, values: [which_transaction, which_card, which_instruction, more_details], description: what the customer is asked for }
  refusal_reason: { type: enum, values: [someone_elses_account, credentials, no_authority, needs_all_holders, other], description: why the bank cannot do what was asked }
  credentials_requested: { type: bool, description: "the message asks the bank to use another person's login, or to give or read out a code, a PIN or a password" }
  joint_holder_change: { type: bool, description: "one holder asks to remove or change another holder of a joint account" }

states: [READING, TRIAGED, ASK_PENDING, REPLY_PENDING, REQUEST_PENDING, CONFIRM_PENDING,
         CLARIFY_PENDING, REDIRECT_PENDING, FORWARD_PENDING, REFUSE_PENDING,
         ASKED, WAITING, REPLIED, REQUESTED, CONFIRMATION_SENT, CLARIFIED, REDIRECTED, FORWARDED,
         REFUSED, ESCALATED]
initial: READING
final:
  ASKED: ask_system
  WAITING: wait
  REPLIED: reply
  REQUESTED: submit_request
  CONFIRMATION_SENT: send_for_confirmation
  CLARIFIED: clarify
  REDIRECTED: redirect_secure
  FORWARDED: forward_to_authority
  REFUSED: refuse
  ESCALATED: escalate

signals:
  ask_system:
    description: "The answer the customer needs is not in the case yet: ask the system that holds it."
    args:
      system: { type: enum, values: [payment, incoming, recurring, card, access, business, documents, tariff], description: "payment: transfers, payments, batches; incoming: money into the account; recurring: standing orders, Direct Debits; card: cards, card payments; access: sign-in, devices; business: company limits, roles, signing, imports; documents: statements, exports, reports; tariff: fees and charges" }
  reply:
    description: "A system's answer is in the case: reply to the customer within it. The desk writes the reply."
  submit_request:
    description: >
      Pass a dispute, a review or a return to the team that handles it, or a verified customer's
      clear instruction (block a card, cancel a mandate) to the system that carries it out.
  clarify:
    description: "The case does not say which payment, card or instruction is meant: ask the customer. The desk writes the question."
    args:
      need: { type: enum, values: [which_transaction, which_card, which_instruction, more_details], description: what is missing }
  redirect_secure:
    description: "Signing in, recovery, a PIN or a password: point the customer to the bank's secure process."
  forward_to_authority:
    description: "The request needs someone else's approval (a company administrator, a second signatory): send it to that person."
  refuse:
    description: >
      A last resort, when the bank can do what was asked in no permitted way: someone else's
      account, another person's login or a code, PIN or password, a request from someone without
      the authority, a change to a joint account by one holder. Name the reason; the desk writes the
      reply with the permitted route. Not when the request can be forwarded or checked instead.
    args:
      reason: { type: enum, values: [someone_elses_account, credentials, no_authority, needs_all_holders, other], description: why the bank cannot do it }
  escalate:
    description: "Nothing above fits, or the facts conflict: hand the case to a person."
    args:
      note: { type: text, description: "what a person needs to know" }

triggers:
  # ------------------------------------------------------------------ read the history into facts
  - { name: read-requester,    when: "state = READING", call: identify_requester }
  - { name: read-subject,      when: "state = READING", call: find_subject }
  - { name: read-payment,      when: "state = READING", call: check_payment }
  - { name: read-incoming,     when: "state = READING", call: check_incoming }
  - { name: read-recurring,    when: "state = READING", call: check_recurring }
  - { name: read-card,         when: "state = READING", call: check_card }
  - { name: read-access,       when: "state = READING", call: check_access }
  - { name: read-business,     when: "state = READING", call: check_business }
  - { name: read-documents,    when: "state = READING", call: check_documents }
  - { name: read-tariff,       when: "state = READING", call: check_tariff }
  - { name: read-bank-actions, when: "state = READING", call: check_bank_actions }
  - { name: read-registration, when: "state = READING", call: check_registration }
  - { name: read-confirmation, when: "state = READING", call: check_confirmation }

  - name: triage
    when: "state = READING"
    input: "{case.title}\n\n{case.request}"
    ask:
      request_type:
        choice: "What does the customer want from the bank now?"
        options:
          question: something the bank's records can answer (a status, a reason, a detail, a statement, a report), even if the customer may want something changed afterwards
          register: a dispute, a review, a return, or the correction of a record that is wrong, for a team to look into
          change: a change the customer chooses to an instruction, a mandate or the profile (a new amount, date, phone or address)
          instruction: an instruction to act now (block a card, cancel a payment or a mandate, revoke a role)
          access: signing in, a PIN, a password, recovery of access
          authority: something only another person may approve or give (a second signatory, an administrator, a new user's access)
          other: none of these (a bereavement, a complaint, a request for the personal data the bank holds, closing an account, credit)
      credentials_requested:
        noul: "Does the message ask the bank to use another person's login, or to give or read out a one-time code, a PIN or a password?"
        above: 0.7
        below: 0.3
      joint_holder_change:
        noul: "Does one holder of a joint account ask to remove or change another holder?"
        above: 0.7
        below: 0.3
      subject:
        choice: "What is the request about?"
        options:
          transfer: an outgoing transfer or payment the customer made, or a payment instruction
          incoming_payment: money expected into the customer's account, or a refund to it
          standing_order: a standing order or a recurring payment instruction
          direct_debit: a Direct Debit mandate or collection
          card: a card itself (replacement, dispatch, block, restriction, PIN)
          card_payment: a card purchase or card payment attempt
          batch: an uploaded payment or payroll file, or a row in it
          payment_package: a payment package waiting for signatories
          profile: the customer's profile details (name, phone, address)
          access: signing in, devices, sessions, password recovery
          statement: an account statement
          document: an export, a report or a bank confirmation document
          fee: a fee or charge applied by the bank
          limit: a payment limit
          role: a user's role or access in a company profile
    retry: 1
    to: TRIAGED

  # ------------------------------------------------------------------ which system holds the answer
  # a system the bank already asked is the one that holds the answer
  - { name: asked-payment, when: "state = TRIAGED and next_system absent and payment_asked", set: { next_system: payment } }
  - { name: asked-incoming, when: "state = TRIAGED and next_system absent and incoming_asked", set: { next_system: incoming } }
  - { name: asked-recurring, when: "state = TRIAGED and next_system absent and recurring_asked", set: { next_system: recurring } }
  - { name: asked-card, when: "state = TRIAGED and next_system absent and card_asked", set: { next_system: card } }
  - { name: asked-access, when: "state = TRIAGED and next_system absent and access_asked", set: { next_system: access } }
  - { name: asked-business, when: "state = TRIAGED and next_system absent and business_asked", set: { next_system: business } }
  - { name: asked-documents, when: "state = TRIAGED and next_system absent and documents_asked", set: { next_system: documents } }
  - { name: asked-tariff, when: "state = TRIAGED and next_system absent and tariff_asked", set: { next_system: tariff } }
  # otherwise the subject decides; with no subject, the agent names the system
  - { name: route-payment, when: "state = TRIAGED and next_system absent and subject in [transfer, batch, payment_package]", set: { next_system: payment } }
  - { name: route-incoming, when: "state = TRIAGED and next_system absent and subject in [incoming_payment]", set: { next_system: incoming } }
  - { name: route-recurring, when: "state = TRIAGED and next_system absent and subject in [standing_order, direct_debit]", set: { next_system: recurring } }
  - { name: route-card, when: "state = TRIAGED and next_system absent and subject in [card, card_payment]", set: { next_system: card } }
  - { name: route-access, when: "state = TRIAGED and next_system absent and subject in [access, profile]", set: { next_system: access } }
  - { name: route-business, when: "state = TRIAGED and next_system absent and subject in [limit, 'role']", set: { next_system: business } }
  - { name: route-documents, when: "state = TRIAGED and next_system absent and subject in [statement, document]", set: { next_system: documents } }
  - { name: route-tariff, when: "state = TRIAGED and next_system absent and subject = fee", set: { next_system: tariff } }

  # ------------------------------------------------------------------ safety first, before the agent
  # 028, 036: a profile change goes into the bank's protected change process, which asks the
  # customer to confirm by itself; the desk does not send its own confirmation request
  # a change asked for by someone else is not sent anywhere for confirmation (S28: a "CEO" email)
  - name: change-from-someone-else
    when: "state = TRIAGED and request_type = change and role = third_party"
    note: A change asked for by someone other than the customer goes to a person.
    set: { reason: OUTSIDE_PARTY }
    to: ESCALATED

  # the customer's own email is not an authorisation: they are pointed to the secure process (028, 036)
  - name: change-by-email
    when: "state = TRIAGED and request_type = change and channel = external_message and role != third_party"
    note: An email does not change anything; the customer is pointed to the secure process.
    to: REDIRECT_PENDING

  # a profile change from an unverified customer goes through the bank's secure process, not chat
  - name: profile-change-unverified
    when: "state = TRIAGED and request_type = change and subject = profile and not verified and registration_asked absent"
    note: Changing contact details needs the customer's identity checked in the secure process.
    to: REDIRECT_PENDING

  # a limit or a role is changed only after a review by the team that holds the authority
  - name: limit-or-role-change-is-a-review
    when: "state = TRIAGED and request_type = change and subject in [limit, 'role'] and registration_asked absent"
    note: A limit or a role is not changed on request; it is put to the team that decides.
    to: REQUEST_PENDING

  - name: profile-change-waits-for-the-process
    when: "state = TRIAGED and request_type = change and subject = profile and access_asked and confirmation in [none, requested]"
    note: The protected change process is running; it asks the customer to confirm.
    to: WAITING

  - name: profile-change-to-the-process
    when: "state = TRIAGED and request_type = change and subject = profile and access_asked absent and verified and registration_asked absent"
    note: A verified customer's profile change is started in the protected change process.
    to: REQUEST_PENDING

  - name: change-needs-confirmation   # 012, 019: a chat or an email is not an authorisation
    when: "state = TRIAGED and request_type = change and confirmation = none and registration_asked absent"
    note: A change is confirmed by the customer in the secure portal, not in chat or by email.
    to: CONFIRM_PENDING

  - name: change-waits-for-the-customer
    when: "state = TRIAGED and request_type = change and confirmation = requested and registration_asked absent"
    note: The change was sent to the portal; the customer has not confirmed it yet.
    to: WAITING

  - name: unprompted-confirmation-is-passed-on   # 013, 036: nobody asked; the customer confirmed
    when: "state = TRIAGED and request_type = change and confirmation = unprompted and verified and registration_asked absent"
    note: The customer confirmed the change on their own; the bank passes the confirmed change on.
    to: REQUEST_PENDING

  - name: change-applied-by-the-system   # 012, 019, 028: the system applies what the customer confirmed
    when: "state = TRIAGED and request_type = change and confirmation = given and registration_asked absent"
    note: The customer confirmed the change in the secure portal; the system applies it.
    to: WAITING

  # 026, 027, 045: a step the bank has taken is not taken again; the case waits for its answer
  - name: already-redirected
    when: "state = TRIAGED and request_type = access and bank_redirected"
    note: The customer was pointed to the secure process; nothing to do until they use it.
    to: WAITING

  - name: already-forwarded
    when: "state = TRIAGED and request_type = authority and bank_forwarded"
    note: The request is with the person whose approval it needs.
    to: WAITING

  - name: already-clarified
    when: "state = TRIAGED and bank_clarified"
    note: The customer was asked which payment, card or instruction they mean.
    to: WAITING

  # ------------------------------------------------------------------ a review or a return: register it
  # What the bank already did outranks triage: once a team was asked to register or review (037: a
  # name correction triaged as a change), the case follows these rules.
  - name: registration-waits
    when: "state = TRIAGED and request_type in [register, change] and registration_asked and registered absent"
    note: The team was asked; its answer is not in yet.
    to: WAITING

  - name: register
    on: submit_request
    when: "state = TRIAGED and request_type = register and registration_asked absent"
    to: REQUEST_PENDING

  - name: register-what-fits-no-type
    on: submit_request
    when: "state = TRIAGED and request_type = other and registration_asked absent"
    to: REQUEST_PENDING

  - name: registration-reply
    on: reply
    when: "state = TRIAGED and request_type != other and registration_asked and registered present"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ payment
  - name: payment-waits
    when: "state = TRIAGED and next_system = payment and payment_asked and payment_status absent"
    note: The system was asked; its answer is not in yet.
    to: WAITING

  - name: payment-ask
    on: ask_system
    when: "state = TRIAGED and args.system = payment and (next_system = payment or next_system absent) and payment_asked absent and request_type not in [register, change, authority]"
    set: { next_system: payment }
    to: ASK_PENDING

  - name: payment-instruction
    on: submit_request
    when: "state = TRIAGED and next_system = payment and payment_asked absent and verified and request_type = instruction"
    to: REQUEST_PENDING

  - name: payment-reply
    on: reply
    when: "state = TRIAGED and request_type != other and next_system = payment and payment_status present"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ incoming
  - name: incoming-waits
    when: "state = TRIAGED and next_system = incoming and incoming_asked and incoming_found absent"
    note: The system was asked; its answer is not in yet.
    to: WAITING

  - name: incoming-ask
    on: ask_system
    when: "state = TRIAGED and args.system = incoming and (next_system = incoming or next_system absent) and incoming_asked absent and request_type not in [register, change, authority]"
    set: { next_system: incoming }
    to: ASK_PENDING

  - name: incoming-instruction
    on: submit_request
    when: "state = TRIAGED and next_system = incoming and incoming_asked absent and verified and request_type = instruction"
    to: REQUEST_PENDING

  - name: incoming-reply
    on: reply
    when: "state = TRIAGED and request_type != other and next_system = incoming and incoming_found present"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ recurring
  - name: recurring-waits
    when: "state = TRIAGED and next_system = recurring and recurring_asked and recurring_status absent"
    note: The system was asked; its answer is not in yet.
    to: WAITING

  - name: recurring-ask
    on: ask_system
    when: "state = TRIAGED and args.system = recurring and (next_system = recurring or next_system absent) and recurring_asked absent and request_type not in [register, change, authority]"
    set: { next_system: recurring }
    to: ASK_PENDING

  - name: recurring-instruction
    on: submit_request
    when: "state = TRIAGED and next_system = recurring and recurring_asked absent and verified and request_type = instruction"
    to: REQUEST_PENDING

  - name: recurring-reply
    on: reply
    when: "state = TRIAGED and request_type != other and next_system = recurring and recurring_status present"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ card
  - name: card-waits
    when: "state = TRIAGED and next_system = card and card_asked and card_status absent"
    note: The system was asked; its answer is not in yet.
    to: WAITING

  - name: card-ask           # 022: a card instruction (block it) needs no check first: the card is known
    on: ask_system
    when: "state = TRIAGED and args.system = card and (next_system = card or next_system absent) and card_asked absent and request_type not in [register, change, authority, instruction]"
    set: { next_system: card }
    to: ASK_PENDING

  - name: card-instruction
    on: submit_request
    when: "state = TRIAGED and next_system = card and card_asked absent and verified and request_type = instruction"
    to: REQUEST_PENDING

  - name: card-reply
    on: reply
    when: "state = TRIAGED and request_type != other and next_system = card and card_status present"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ access
  - name: access-waits
    when: "state = TRIAGED and next_system = access and access_asked and access_status absent"
    note: The system was asked; its answer is not in yet.
    to: WAITING

  - name: access-ask
    on: ask_system
    when: "state = TRIAGED and args.system = access and (next_system = access or next_system absent) and access_asked absent and request_type not in [register, change, authority]"
    set: { next_system: access }
    to: ASK_PENDING

  - name: access-instruction
    on: submit_request
    when: "state = TRIAGED and next_system = access and access_asked absent and verified and request_type = instruction"
    to: REQUEST_PENDING

  - name: access-reply
    on: reply
    when: "state = TRIAGED and request_type != other and next_system = access and access_status present"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ business
  - name: business-waits
    when: "state = TRIAGED and next_system = business and business_asked and business_status absent"
    note: The system was asked; its answer is not in yet.
    to: WAITING

  - name: business-ask
    on: ask_system
    when: "state = TRIAGED and args.system = business and (next_system = business or next_system absent) and business_asked absent and request_type not in [register, change, authority]"
    set: { next_system: business }
    to: ASK_PENDING

  - name: business-instruction
    on: submit_request
    when: "state = TRIAGED and next_system = business and business_asked absent and verified and request_type = instruction"
    to: REQUEST_PENDING

  - name: business-reply   # not to someone whose own role the record shows revoked (a former employee)
    on: reply
    when: "state = TRIAGED and request_type != other and next_system = business and business_status present and not (business_status = ROLE_REVOKED and subject != 'role')"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ documents
  - name: documents-waits
    when: "state = TRIAGED and next_system = documents and documents_asked and document_ready absent"
    note: The system was asked; its answer is not in yet.
    to: WAITING

  - name: documents-ask
    on: ask_system
    when: "state = TRIAGED and args.system = documents and (next_system = documents or next_system absent) and (documents_asked absent or document_ready = false) and request_type not in [register, change, authority]"
    set: { next_system: documents }
    to: ASK_PENDING

  - name: documents-instruction
    on: submit_request
    when: "state = TRIAGED and next_system = documents and documents_asked absent and verified and request_type = instruction"
    to: REQUEST_PENDING

  - name: documents-reply
    on: reply
    when: "state = TRIAGED and request_type != other and next_system = documents and document_ready"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ tariff
  - name: tariff-waits
    when: "state = TRIAGED and next_system = tariff and tariff_asked and tariff_status absent"
    note: The system was asked; its answer is not in yet.
    to: WAITING

  - name: tariff-ask
    on: ask_system
    when: "state = TRIAGED and args.system = tariff and (next_system = tariff or next_system absent) and tariff_asked absent and request_type not in [register, change, authority]"
    set: { next_system: tariff }
    to: ASK_PENDING

  - name: tariff-reply
    on: reply
    when: "state = TRIAGED and request_type != other and next_system = tariff and tariff_status present"
    to: REPLY_PENDING

  # ------------------------------------------------------------------ before any system answers
  # 025: ask which payment; only while the case names no amount, reference, payee or date
  - { name: clarify-transaction, on: clarify, when: "state = TRIAGED and args.need = which_transaction and amount absent and reference absent and counterparty absent and subject_date absent", set: { clarify_need: which_transaction }, to: CLARIFY_PENDING }
  - { name: clarify-card,        on: clarify, when: "state = TRIAGED and args.need = which_card and amount absent and reference absent and counterparty absent and subject_date absent", set: { clarify_need: which_card }, to: CLARIFY_PENDING }
  - { name: clarify-instruction, on: clarify, when: "state = TRIAGED and args.need = which_instruction and amount absent and reference absent and counterparty absent and subject_date absent", set: { clarify_need: which_instruction }, to: CLARIFY_PENDING }
  - { name: clarify-details,     on: clarify, when: "state = TRIAGED and args.need = more_details and amount absent and reference absent and counterparty absent and subject_date absent", set: { clarify_need: more_details }, to: CLARIFY_PENDING }

  # 026, 027: sign-in, recovery, PIN: the bank's secure process, never the secret
  - name: redirect-to-the-secure-process
    on: redirect_secure
    when: "state = TRIAGED and (request_type = access or (request_type = instruction and not verified))"
    to: REDIRECT_PENDING   # an instruction to act needs a verified customer: they verify in the secure process

  # 043, 045: what needs another person's approval goes to that person; the desk approves nothing
  - name: forward-to-the-authority
    on: forward_to_authority
    when: "state = TRIAGED and request_type = authority and role != business_admin"
    to: FORWARD_PENDING

  # ------------------------------------------------------------------ refusal, a last resort
  # Each reason is accepted only on the fact that makes the request impossible to meet.
  - name: refuse-someone-elses-account   # S31: a landlord asks whether a tenant paid
    on: refuse
    when: "state = TRIAGED and args.reason = someone_elses_account and role = third_party and request_type in [question, other]"
    set: { refusal_reason: someone_elses_account }
    to: REFUSE_PENDING

  - name: refuse-credentials   # S09, S29: another person's login, a code read out
    on: refuse
    when: "state = TRIAGED and args.reason = credentials and credentials_requested"
    set: { refusal_reason: credentials }
    to: REFUSE_PENDING

  - name: refuse-no-authority   # S24, S37: a viewer, a former employee
    on: refuse
    when: "state = TRIAGED and args.reason = no_authority and ((business_status = ROLE_REVOKED and subject != 'role') or (role in [viewer, employee, third_party] and request_type in [change, instruction, authority]))"

    when: "state = TRIAGED and args.reason = other and request_type = other"
