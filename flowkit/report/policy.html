THE CONTRACT

The agent asks.
The policy decides.

A bank's service desk (Harrow & Vale Bank, fictional). A case is a customer's request and what happened since, up to now. The desk decides the bank's next step: ask the internal system that holds the answer, wait for an answer already asked for, reply within what a record shows, pass a request or a verified instruction to the team or system that handles it, send a change to the customer's secure portal to confirm, or hand the case to a person. The bank never acts for a customer, never approves for someone else, never handles a PIN or a password, and never claims more than a record shows.

04 / WHAT THE AGENT CAN ASK

4 tools. Bounded authority.

ask_system

Ask the internal system that holds the answer the customer needs, when that answer is not in the case yet. Name the system. The desk asks it about the case's subject; the answer comes later. Not for registering a review or passing on an instruction.

system payment: transfers, payments, batches; incoming: credits to the account; recurring: standing orders and Direct Debits; card: cards and card payments; access: sign-in, devices, PIN and password routes; business: company limits, roles, signing, imports; documents: statements, exports, reports, fees

reply

Reply to the customer now, from what the system's answer in the case shows. The desk writes the reply from the facts: what the record shows, what it does not establish, what was not done. Only when the answer is already in the case.

submit_request

Pass the customer's request to the team or system that handles it: a review, a dispute or a return to be looked into, or the customer's own verified instruction (block a card, cancel a future payment, revoke a role). The bank records and forwards it; it does not decide the review or act on its own authority.

escalate

Hand the case to a person now: when the request needs someone else's authority, asks for a secret, conflicts with the facts, or fits none of the other tools. Say what a person needs to know.

note what happened and what is still open, for the person

# The banking track's policy: what the bank does next at one decision point of a case.
# Design: docs/policy-design.md. Facts come from track/functions.py, which reads the case's
# history (docs/task/target-api.md); the agent reads the conversation and the facts and sends the
# decision as a signal; a rule accepts it only when the facts support it.
#
# Convention: a rule with `on:` only moves the case (`set:`, `to:`); the work is done by a rule
# with no `on:`, fired by the state, once. Every final state is a decision.

policy: banking-desk
version: 1
description: >
  A bank's service desk (Harrow & Vale Bank, fictional). A case is a customer's request and what
  happened since, up to now. The desk decides the bank's next step: ask the internal system that
  holds the answer, wait for an answer already asked for, reply within what a record shows, pass
  a request or a verified instruction to the team or system that handles it, send a change to the
  customer's secure portal to confirm, or hand the case to a person. The bank never acts for a
  customer, never approves for someone else, never handles a PIN or a password, and never claims
  more than a record shows.

fields:
  # --- who is asking (identify_requester)
  requester: { type: text, description: the customer's name as written }
  role:      enum [customer, business_admin, signatory, uploader, viewer, employee, third_party]
  channel:   enum [secure_portal, secure_chat, verified_call, business_portal, external_message]
  verified:  { type: bool, description: the request came through a verified channel or after identity checks }
  # --- what it is about (find_subject)
  subject:      enum [transfer, incoming_payment, standing_order, direct_debit, card, card_payment, batch, payment_package, profile, access, statement, document, fee, limit, role]
  amount:       money
  counterparty: text
  reference:    text
  subject_date: date
  # --- what the systems answered (check_*)
  payment_asked:      bool
  payment_status:     enum [SENT, PENDING, AWAITING_AUTHORISATION, COMPLETED, DECLINED, NOT_EXECUTED, REJECTED, CANCELLED, OTHER]
  payment_reason:     text
  payment_count:      number
  incoming_asked:     bool
  incoming_found:     bool
  incoming_amount:    money
  recurring_asked:    bool
  recurring_status:   enum [ACTIVE, CANCELLED, NOT_EXECUTED, AMENDED, OTHER]
  next_run:           date
  card_asked:         bool
  card_status:        enum [REQUESTED, IN_MANUFACTURE, DISPATCHED, BLOCKED, RESTRICTED, DECLINED, OTHER]
  card_reason:        text
  access_asked:       bool
  access_status:      enum [RESTORED, AWAITING_CONFIRMATION, LINKED, PROCEDURE_STARTED, EXTRACT_PROVIDED, OTHER]
  business_asked:     bool
  business_status:    enum [RECEIVED, VALIDATION_FAILED, AWAITING_SECOND_SIGNATORY, PENDING_APPROVAL, ROLE_REVOKED, OTHER]
  business_limit:     money
  documents_asked:    bool
  document_ready:     bool
  document_name:      text

  instructed_outside_portal: bool
  # --- the policy's own
  request_type: enum [status, reason, record_fact, register, change, instruction, document, access, authority]
  next_system:  { type: enum, values: [payment, incoming, recurring, card, access, business, documents], description: the system that holds the answer }
  reason:       enum [NO_AUTHORITY, UNVERIFIED, AGENT_ESCALATED, ACTION_FAILED, NOT_HANDLED]

states: [READING, TRIAGED, ASK_PENDING, REPLY_PENDING, REQUEST_PENDING, CONFIRM_PENDING,
         ASKED, WAITING, REPLIED, REQUESTED, CONFIRMATION_SENT, ESCALATED]

  WAITING: wait

triggers:
  # ------------------------------------------------------------------ read the history into facts
  - { name: read-requester,    when: "state = READING", call: identify_requester }
  - { name: read-subject,      when: "state = READING", call: find_subject }
  - { name: read-payment,      when: "state = READING", call: check_payment }
  - { name: read-incoming,     when: "state = READING", call: check_incoming }
  - { name: read-recurring,    when: "state = READING", call: check_recurring }
  - { name: read-card,         when: "state = READING", call: check_card }
  - { name: read-access,       when: "state = READING", call: check_access }
  - { name: read-business,     when: "state = READING", call: check_business }
  - { name: read-documents,    when: "state = READING", call: check_documents }
  - { name: read-registration, when: "state = READING", call: check_registration }
  - { name: read-confirmation, when: "state = READING", call: check_confirmation }

  - name: triage
    when: "state = READING"
    input: "{case.title}\n\n{case.request}"
    ask:
      request_type:
        choice: "What does the customer want from the bank now?"
        options:
          status: the stage or status of a payment, card, file, device or request
          reason: why something was declined, restricted or did not run
          record_fact: a detail from a record (a date, a purpose, an amount, a limit, a fee, a mandate, active instructions)
          register: a dispute, a review, a correction or a return to be looked into by a team
          change: a change to a payment instruction, a mandate, an amount, a date or the profile (phone, address)
          instruction: an instruction to act now (block a card, cancel a payment or a mandate, revoke a role)
          document: a statement, an export, a report or a confirmation made available in the portal
          access: signing in, a PIN, a password, recovery of access
          authority: something only another person may approve or give (a second signatory, an administrator, a new user's access)
      subject:
        choice: "What is the request about?"
        options:
          transfer: an outgoing transfer or payment the customer made, or a payment instruction
          incoming_payment: money expected into the customer's account, or a refund to it
          standing_order: a standing order or a recurring payment instruction
          direct_debit: a Direct Debit mandate or collection
          card: a card itself (replacement, dispatch, block, restriction, PIN)
          card_payment: a card purchase or card payment attempt
          batch: an uploaded payment or payroll file, or a row in it
          payment_package: a payment package waiting for signatories
          profile: the customer's profile details (name, phone, address)
          access: signing in, devices, sessions, password recovery
          statement: an account statement
          document: an export, a report or a bank confirmation document
          fee: a fee or charge applied by the bank
          limit: a payment limit
